# What the client asks for, and who it asks — 2026-09-11

Measured, not read off the source: `node devtools/api-audit.mjs`, which boots
the real bundle under the harness and records every request the page issues,
whoever issued it (fetch, `<img>`, a texture loader, a worker, a script tag).
Three runs, all `--nodraw`, JSON kept beside each table below.

The question was which client data sources bypass the cell's S3 read-through
cache — the `~/` routes in `index.ts`, where CloudFront reads the public
namespace first and the Lambda banks what it had to compute (`putTile`).

---

## The answer in one line

**Elevation is the whole finding.** Every other data source the client reads
already goes through a `~/` route. The DEM does not, has no route at all, and
is by a wide margin the largest source by both request count and bytes.

Cell columns exclude the page shell and `app.js`, which are the bundle, not
data.

| run | through the cell | third-party direct | DEM's share of bytes |
|---|---|---|---|
| Cape Town, 40 sim s | 113 req / 3.93 MB | 85 req / 2.29 MB — **83 of them DEM** | 37% |
| Machu Picchu (cold), 25 sim s | 100 req / 0.56 MB | 89 req / 9.01 MB — **87 of them DEM** | 94% |
| random spawn, 25 sim s | 184 req / 0.52 MB | 147 req / 12.44 MB — 136 DEM, 8 Overpass | 96% |

Cape Town is the friendly case: a dense city makes the vector tiles heavy
enough to be comparable. Everywhere else the DEM *is* the network.

Weather is one request per fifteen minutes and reverse geocode is one per
session; both are direct and neither is worth a route on volume alone. DEM is
80–90 requests in the first half-minute of driving.

## Source by source

### Through the cache, working as designed

| route | upstream the cell hides | seen |
|---|---|---|
| `~/osm/v4/{z}/{x}/{y}` | Overpass mirrors | 20–33 req/run |
| `~/osm/ov1/`, `~/osm/peak1/` | Overpass (overview, summits) | 1–2 req/run |
| `~/cover/v1/` | ESA WorldCover COGs on S3 (range-read + TIFF decode) | 74 req/run |
| `~/eco/v1/` | RESOLVE Ecoregions on ArcGIS | 1–2 req/run |
| `~/campaign/`, `~/tape/v1/` | the cell's own data | 1/run |

Nothing to do here. Note the shape of the cover row: 74 requests for 0.3–0.4 MB
is the cheapest data in the game precisely *because* it is banked — those same
74 tiles are a COG range-read and a TIFF decode per tile when they miss.

### Straight to a third party, with no route behind it

| host | what | volume | verdict |
|---|---|---|---|
| `tiles.mapterhorn.com` | terrarium height tiles, z14, 512px webp | 83–136 req, 2–12 MB per short drive | **should be cached, is not** |
| `s3.amazonaws.com/elevation-tiles-prod` | the legacy AWS DEM, fallback when Mapterhorn 404s | 0 in these runs (Mapterhorn answered) | same |
| `nominatim.openstreetmap.org` | reverse geocode of the spawn, for the place name | 1–2 per session | low volume, still uncached |
| `api.open-meteo.com` | cloud, rain, wind at the origin | 1 per 15 min | low volume, still uncached |

`esm.sh` and `cdn.jsdelivr.net` also appear: those are CODE (three.js, ez-tree,
eruda on demand), not data, and are out of scope for a read-through cache.

### Direct by design, not a defect

`findSpawn` (`?random=1` only) POSTs `way["highway"](around:2500,…);out ids 8`
straight to the Overpass mirrors — four probes, one per candidate coordinate.
There is no tile to key an S3 object on, so there is nothing for the cache to
hold. The audit tool separates these from tile traffic by the query body so
they stop being counted against `~/osm/v4/`.

## The elevation gap, in detail

`fetchMapterhorn` (`client/main.ts:716`) and the AWS fallback below it are the
only two world fetches that do not name `CELL_BASE`. `index.ts` has no `~/dem/`
route; `TILE_RE`, `COVER_RE`, `OV_RE`, `PEAK_RE`, `ECO_RE` and `CAMPAIGN_RE` are
the complete list, so there is no path in the cell that a DEM request could
take even if the client asked for one.

What that costs, as measured:

- **2.2 MB at Cape Town, 8.8 MB at Machu Picchu, 11.9 MB at a random spawn** —
  in 25–40 seconds of driving each, from the device, every session, per player.
  It is 37% of the game's data bytes in a dense city and 94–96% everywhere
  else.
- Every one of those is a **live hit on Mapterhorn's infrastructure**, which is
  a volunteer aggregation of national elevation surveys. The cover, vector and
  ecoregion layers ask their upstreams once for everybody; the DEM asks once
  per player per tile.
- The **pyramid climb multiplies it**. Where a z14 tile is absent the client
  walks up to z6, one request per level, each of which 404s. A route could
  answer the climb from one banked object; today each refusal is a round trip.
- It is the one source whose **CSP exposure is unavoidable**: `connect-src` has
  to carry `tiles.mapterhorn.com` and `s3.amazonaws.com` forever because the
  client talks to them by name. Everything else could, in principle, be
  `'self'` plus the apex.

The client-side caching that does exist — `readRaster`/`writeRaster`, keyed by
source URL in `drive-cache` — is per-device and does nothing for a cold player.
It is the reason a returning session is cheap and the reason this was easy to
miss.

### What a `~/dem/v1/{z}/{x}/{y}` route would look like

The cover route is the template: the cell already fetches upstream bytes,
transforms them and banks the result. A DEM route is strictly simpler — no COG
range-read, no TIFF decode, just a proxy of the webp with the pyramid climb
moved server-side, so a miss returns the ancestor that exists and banks it under
the requested key. The cell gets the `putTile` for free and the client loses a
loop.

Not done here: this is an audit, and the route is a change to the deploy
surface (a new path under `~/`, a `connect-src` line that can then be dropped,
and a client cutover with the direct fetch kept as the bad-deploy fallback,
exactly as `proxyTile` keeps the Overpass mirrors).

## A rig defect found on the way, and fixed

`devtools/harness.mjs` proxied `/~/osm/v3/` to the deployed cell. The client
moved to `~/osm/v4/` (water relations) and the harness was never updated, so
**every fine vector tile 404'd locally and every harness run has been silently
driving the client's Overpass mirror fallback** — the exact thing the comment
above that branch says it stopped being. The first audit run showed it: 30
`~/osm/v4/` requests, none answered, and a pile of direct Overpass traffic.

Matched by shape now (`/^\/~\/osm\/v\d+\//`, as the cell's own `TILE_RE`
accepts v2–v4). After the fix the same run reads 33 fine tiles through the cell
and zero Overpass. Anything measured against the mirrors rather than the banked
route — road density, stream timing, tile latency — was measuring a different
source than the phone uses.

## Running it

```
node devtools/api-audit.mjs [--spot='lat=…&lon=…'] [--drive=<sim seconds>]
                            [--nodraw] [--json=<path>]
```

The `KNOWN` table in the tool is the audit's opinion, and a host that is not in
it prints as `UNCLASSIFIED` — so a new upstream added to the client shows up
here as a line nobody wrote.

**What it cannot tell you**, and the harness header says why: whether a host is
REACHABLE from a phone. Every off-origin request is relayed through curl and
never faces the page's CSP, so a host the policy forbids is answered here
anyway. This measures what is ASKED FOR, which is the question the cache audit
needed. Reachability is `devtools/shell-server.mjs` or a device.
